# 게임 개발 동아리 운영 콘솔 기능 기획서

- 작성일: 2026-08-05
- 대상: 구현 담당 팀원
- 문서 목적: 구현할 기능, 데이터 구조, 판정 규칙, 완료 기준을 한 문서에서 확인한다.

## 1. 제품 개요

### 1-1. 해결하려는 문제

동아리 임원이 회원, 팀, 일정, 활동과 출석 기록을 여러 문서에 나누어 관리하면 다음 문제가 생긴다.

- 한 팀에 인원이 지나치게 몰린 사실을 늦게 발견한다.
- 해커톤이나 축제 같은 예정 일정을 놓치기 쉽다.
- 반복적으로 무단 불참하는 회원을 객관적인 기록 없이 판단하게 된다.
- 팀별·개인별 활동량을 바로 파악하기 어렵다.

이 웹앱은 위 정보를 한 브라우저에서 연결해 관리하고, 임원이 확인해야 할 운영 위험을 대시보드에 보여준다.

### 1-2. 사용자와 사용 환경

- 주 사용자: 게임 개발 동아리 임원 1명
- 사용 방식: 임원이 한 브라우저에서 직접 회원과 활동 정보를 입력하고 조회한다.
- 저장 방식: 별도 로그인, 서버, 데이터베이스 없이 브라우저 `localStorage`에 저장한다.
- 주요 사용 시점: 팀 편성, 활동 일정 계획, 활동 종료 후 출석 기록, 주간 운영 현황 확인

### 1-3. 제품 목표

1. 회원을 게임 개발 직군과 함께 등록하고 팀별로 관리한다.
2. 팀별 권장 정원을 기준으로 인원 과밀을 조기에 알린다.
3. 미래 일정과 완료된 활동 기록을 분리하되 서로 연결한다.
4. 실제 출석 기록을 바탕으로 연속 노쇼 위험을 근거와 함께 보여준다.
5. 기간별 활동과 팀·개인별 주간 활동량을 빠르게 확인한다.

### 1-4. 구현 범위에서 제외하는 기능

- 회원 자동 매칭 및 팀 자동 편성
- 회원 자동 제명 또는 제명 결정
- 활동명·장소 키워드 검색
- 월간 캘린더
- JSON 내보내기·가져오기
- 회원 및 팀 정보 수정
- 사용자 계정, 권한 관리, 서버 동기화

앱은 판단을 대신하지 않는다. 정원 초과와 연속 노쇼의 근거만 제공하고 최종 판단은 임원이 한다.

## 2. 핵심 사용자 흐름

### 2-1. 초기 설정

1. 임원이 팀 이름과 권장 정원을 등록한다.
2. 회원 이름과 직군을 등록한다.
3. 회원을 팀에 배정한다.
4. 정원을 넘겨 배정해도 저장은 허용하되 즉시 경고한다.

### 2-2. 일정에서 활동 기록으로 전환

1. 임원이 해커톤, 축제, 정기활동 등의 미래 일정을 등록한다.
2. 대시보드와 일정 화면에서 가까운 일정을 D-day 순으로 확인한다.
3. 일정이 끝나면 `활동으로 기록`을 선택한다.
4. 일정의 활동명, 날짜, 장소, 대상 팀, 메모를 활동 등록 폼에 복사한다.
5. 임원이 회원별 출석 상태를 확정하고 활동을 저장한다.
6. 변환된 일정에는 연결된 활동 ID를 저장해 중복 변환을 막는다.

### 2-3. 운영 위험 확인

1. 임원이 활동마다 회원의 출석 상태를 기록한다.
2. 앱이 최근 기록을 기준으로 연속 무단 불참을 다시 계산한다.
3. 무단 불참 2회 연속인 회원을 대시보드에 표시한다.
4. 경고 카드에서 판정 근거가 된 활동명과 날짜를 확인한다.
5. 활동을 삭제하면 관련 경고와 통계도 즉시 다시 계산한다.

## 3. 화면 구성

앱은 `대시보드`, `일정`, `활동`, `회원·팀`의 네 화면으로 구성한다.

### 3-1. 대시보드

임원이 앱을 열었을 때 가장 먼저 운영 상태를 확인하는 화면이다.

- 다가오는 일정: 오늘 이후의 미완료 일정을 가까운 날짜순으로 표시
- 정원 초과 팀: 팀 이름, 현재 인원, 권장 정원, 초과 인원 표시
- 연속 노쇼 위험: 회원 이름, 소속 팀, 근거 활동 2건 표시
- 주간 활동 차트: `팀별`과 `개인별` 보기를 토글로 전환
- 데이터가 없을 때 회원·팀 또는 일정을 먼저 등록하도록 안내

### 3-2. 일정

미래에 진행할 행사를 등록하고 활동 기록으로 연결하는 화면이다.

입력 항목:

- 일정명: 필수
- 날짜: 필수, 등록 시점의 오늘 또는 미래만 허용
- 구분: 해커톤, 축제, 정기활동, 기타
- 장소: 선택
- 대상: 전체 동아리 또는 특정 팀
- 메모: 선택

표시 및 동작:

- 미변환 일정은 D-day가 가까운 순서로 표시한다.
- 일정 날짜가 오늘 또는 과거가 되면 `활동으로 기록` 버튼을 제공한다.
- 미래 일정에는 활동 전환 버튼을 표시하지 않는다.
- 변환된 일정은 `기록 완료` 상태와 연결된 활동을 표시한다.
- `convertedActivityId`가 존재하는 일정은 다시 변환할 수 없다.

### 3-3. 활동

완료된 활동과 실제 출석 결과를 저장하는 핵심 화면이다.

입력 항목:

- 활동명: 필수
- 날짜: 필수, 오늘 또는 과거만 허용
- 장소: 선택
- 대상: 전체 동아리 또는 특정 팀
- 참여 회원별 출석 상태
- 참여 인원: `참석` 상태의 회원 수로 자동 계산, 직접 입력하지 않음
- 메모: 선택

출석 상태:

- 전체 동아리 활동이면 등록된 모든 회원을 출석 대상에 표시한다.
- 팀 전용 활동이면 현재 해당 팀에 배정된 회원만 표시한다.
- 출석 대상의 초기 상태는 모두 `미기록`으로 둔다.

| 상태 | 저장 값 | 의미 | 통계·노쇼 반영 |
|---|---|---|---|
| 미기록 | `unmarked` | 아직 확인하지 않음 | 통계 제외, 노쇼 판정 제외 |
| 참석 | `present` | 실제 활동에 참석 | 개인 활동 횟수 포함, 연속 노쇼 초기화 |
| 사전 불참 | `excused` | 미리 사유를 알리고 불참 | 개인 활동 횟수 제외, 연속 노쇼 초기화 |
| 무단 불참 | `noShow` | 사전 연락 없이 불참 | 개인 활동 횟수 제외, 연속 노쇼에 포함 |

목록 및 필터:

- 활동은 날짜 내림차순으로 표시하고, 날짜가 같으면 생성 시각 내림차순으로 표시한다.
- 시작일과 종료일을 지정해 활동 기간을 필터링한다.
- 시작일과 종료일은 결과에 포함한다.
- 필터가 비어 있으면 전체 활동을 표시한다.
- 목록이 비었거나 필터 결과가 없으면 각각 알맞은 안내 문구를 표시한다.
- 삭제 버튼을 누르면 확인 절차를 거친 뒤 해당 활동만 삭제한다.

### 3-4. 회원·팀

회원 명단과 팀 편성을 관리하는 화면이다.

팀 입력 항목:

- 팀 이름: 필수
- 권장 정원: 1 이상의 정수

회원 입력 항목:

- 회원 이름: 필수
- 직군: 기획, 프로그래밍, 아트, 사운드, 기타
- 소속 팀: 팀 등록 전에는 미배정 가능

표시 및 동작:

- 팀 카드에는 현재 인원, 권장 정원, 소속 회원과 직군을 표시한다.
- 현재 인원이 정원을 초과하면 `정원 +N명` 경고 배지를 표시한다.
- 초과 배정은 차단하지 않는다.
- 회원은 한 시점에 한 팀에만 소속될 수 있다.
- 미배정 회원은 별도 목록에 표시한다.

## 4. 데이터 구조

localStorage 키는 아래 네 개로 고정한다. 각 키의 값은 해당 객체의 배열을 JSON 문자열로 저장한다.

### 4-1. 회원 `members`

```js
{
  id: string,
  name: string,
  role: "planning" | "programming" | "art" | "sound" | "other",
  teamId: string | null,
  createdAt: string
}
```

### 4-2. 팀 `teams`

```js
{
  id: string,
  name: string,
  capacity: number,
  createdAt: string
}
```

### 4-3. 일정 `schedules`

```js
{
  id: string,
  title: string,
  date: "YYYY-MM-DD",
  category: "hackathon" | "festival" | "regular" | "other",
  place: string,
  targetTeamId: string | null,
  memo: string,
  convertedActivityId: string | null,
  createdAt: string
}
```

`targetTeamId: null`은 전체 동아리 일정을 의미한다.

### 4-4. 활동 `activities`

```js
{
  id: string,
  title: string,
  date: "YYYY-MM-DD",
  place: string,
  memberCount: number,
  memo: string,
  teamId: string | null,
  attendance: [
    {
      memberId: string,
      status: "unmarked" | "present" | "excused" | "noShow"
    }
  ],
  sourceScheduleId: string | null,
  createdAt: string
}
```

`teamId: null`은 전체 동아리 활동을 의미한다. 기존 요구사항의 필드인 `id`, `title`, `date`, `place`, `memberCount`, `memo`, `createdAt`은 이름을 바꾸거나 제거하지 않는다.

## 5. 판정 및 집계 규칙

### 5-1. 공통 입력 검증

- 문자열 필드는 앞뒤 공백을 제거한 뒤 검증하고 저장한다.
- 활동명, 일정명, 회원 이름, 팀 이름은 공백만 입력할 수 없다.
- 회원 이름과 팀 이름은 대소문자를 구분하지 않고 중복을 막는다.
- 팀 권장 정원은 1 이상의 정수여야 한다.
- 일정 날짜는 등록 시점의 오늘 또는 미래여야 한다.
- 활동 날짜는 브라우저의 현재 지역 날짜보다 미래일 수 없다.
- 활동에는 `present` 상태 회원이 최소 한 명 있어야 한다.

### 5-2. 참여 인원

- 활동 저장 직전에 `attendance`에서 `present`인 항목 수를 계산한다.
- 계산 결과를 `memberCount`에 저장한다.
- 출석 상태가 바뀌면 다음 저장 시 다시 계산한다.

### 5-3. 팀 정원 초과

```text
초과 인원 = 현재 팀 소속 회원 수 - 권장 정원
```

- 초과 인원이 1 이상이면 경고를 표시한다.
- 정원과 같거나 적으면 정상으로 표시한다.
- 경고는 대시보드와 해당 팀 카드에 모두 표시한다.

### 5-4. 연속 노쇼

회원별 판정 절차:

1. 해당 회원의 출석 기록이 있는 활동을 날짜 오름차순으로 정렬한다.
2. 날짜가 같으면 `createdAt` 오름차순으로 정렬한다.
3. `unmarked`는 판정에서 건너뛴다.
4. `noShow`이면 연속 횟수를 1 증가시킨다.
5. `present` 또는 `excused`이면 연속 횟수를 0으로 초기화한다.
6. 최종 연속 횟수가 2 이상이면 위험 회원으로 표시한다.
7. 위험 카드에는 가장 최근의 연속 무단 불참 기록 2건을 근거로 표시한다.

앱은 노쇼 경고를 이유로 회원을 자동으로 삭제하거나 팀에서 제외하지 않는다.

### 5-5. 주간 통계

- 한 주의 기준은 월요일 00:00부터 일요일 23:59까지다.
- 대시보드에는 현재 주의 데이터만 표시한다.
- 개인별 활동 횟수는 해당 회원이 `present`인 활동 수다.
- 팀 전용 활동은 지정된 팀의 활동 1건으로 집계한다.
- 전체 동아리 활동은 `present` 회원이 한 명 이상 있는 각 팀에 활동 1건으로 집계한다.
- 한 활동에 같은 팀 회원이 여러 명 참석해도 그 팀의 활동 횟수는 1만 증가한다.
- 미배정 회원의 참석 기록은 개인 통계에는 포함하지만 팀 통계에는 포함하지 않는다.

### 5-6. 일정 변환

- 일정의 제목, 날짜, 장소, 대상 팀과 메모를 활동 등록 폼에 복사한다.
- 일정 날짜가 미래이면 활동 변환을 허용하지 않는다.
- 임원이 출석 상태를 입력하고 활동 저장을 완료한 뒤에만 일정의 `convertedActivityId`를 갱신한다.
- 활동 저장이 취소되거나 검증에 실패하면 일정은 미변환 상태를 유지한다.
- 변환된 활동을 삭제해도 일정은 자동으로 미변환 상태가 되지 않는다. 일정 카드에는 `연결된 활동이 삭제됨` 상태를 표시해 중복 기록을 방지한다.

## 6. 시각 및 상호작용 원칙

- 전체 화면은 어두운 게임 스튜디오 운영 콘솔 스타일을 사용한다.
- 정상 상태는 청록, 일정 정보는 파랑, 정원 초과는 주황, 노쇼 위험은 빨강으로 표시한다.
- 색상만으로 상태를 구분하지 않고 텍스트와 아이콘 또는 배지를 함께 사용한다.
- 데스크톱에서는 사이드 또는 상단 탭 내비게이션을 사용한다.
- 모바일에서는 한 열로 배치하고, 폼과 카드가 화면 너비를 넘지 않게 한다.
- 빈 화면에는 단순히 `데이터 없음`이라고 쓰지 않고 다음 행동을 안내한다.
- 삭제, 위험 경고처럼 중요한 동작은 일반 등록 버튼과 시각적으로 구분한다.

## 7. 구현 우선순위와 의존 관계

1. **저장 기반**: 네 localStorage 키의 읽기·쓰기와 공통 ID 생성
2. **회원·팀**: 팀 등록, 회원 등록, 팀 배정, 정원 초과 계산
3. **필수 활동 기능**: 등록, 최신순 조회, 삭제 확인, 필수 입력 검증
4. **출석**: 회원별 상태 입력과 `memberCount` 자동 계산
5. **일정**: 일정 등록, D-day 정렬, 활동 폼으로 값 전달, 중복 변환 방지
6. **위험 판정**: 연속 노쇼 계산과 근거 표시
7. **필터·통계**: 기간 필터, 팀별·개인별 주간 통계, Chart.js 차트
8. **대시보드**: 다음 일정, 정원 초과, 노쇼 위험, 통계 통합
9. **마감 작업**: 반응형 레이아웃, 빈 상태, 수동 테스트, README와 보고서 자료

앞 단계의 데이터 구조가 확정되기 전에 다음 단계의 화면만 먼저 만들지 않는다. 시간이 부족하면 8단계의 시각적 장식부터 줄이고 필수 활동 기능과 판정 정확도를 유지한다.

## 8. 테스트 시나리오 및 완료 기준

### 8-1. 활동 필수 기능

- 활동이 없을 때 안내 문구가 표시된다.
- 정상 활동을 저장하면 즉시 목록에 나타난다.
- 여러 활동은 최신 날짜순으로 표시된다.
- 삭제 취소 시 유지되고, 삭제 확인 시 해당 활동만 사라진다.
- 새로고침 후에도 저장된 활동이 유지된다.

### 8-2. 입력 검증

- 빈 활동명과 공백뿐인 활동명은 저장되지 않는다.
- 미래 날짜의 활동은 저장되지 않는다.
- 참석자가 0명이면 저장되지 않는다.
- 정원이 0, 음수, 소수 또는 문자인 팀은 저장되지 않는다.
- 대소문자만 다른 동일 회원명과 팀명은 중복 등록되지 않는다.

### 8-3. 팀 정원

- 현재 인원이 정원 이하이면 경고가 없다.
- 정원을 한 명 넘겨도 배정은 저장된다.
- 팀 카드와 대시보드에 동일한 초과 인원 수가 표시된다.

### 8-4. 노쇼

- 무단 불참 1회만으로는 위험 표시가 생기지 않는다.
- 무단 불참 2회 연속이면 위험 표시와 근거 활동 2건이 나타난다.
- 두 무단 불참 사이에 참석 또는 사전 불참이 있으면 위험 표시가 생기지 않는다.
- `unmarked` 기록은 연속 횟수를 늘리거나 초기화하지 않는다.
- 근거 활동을 삭제하면 위험 판정이 즉시 다시 계산된다.

### 8-5. 일정

- 미래 일정이 D-day가 가까운 순서로 표시된다.
- 일정을 활동으로 전환하면 공통 입력값이 복사된다.
- 활동 저장 전 취소하면 일정은 다시 변환할 수 있다.
- 활동 저장 후 같은 일정의 중복 변환이 차단된다.

### 8-6. 필터와 통계

- 기간 필터는 시작일과 종료일의 활동을 포함한다.
- 팀 전용 활동은 해당 팀에만 1회 집계된다.
- 전체 활동은 참석자가 있는 각 팀에 1회씩 집계된다.
- 한 활동에 같은 팀원 여러 명이 참석해도 팀 횟수는 1회다.
- 개인 통계에는 `present`만 포함된다.
- Chart.js에 전달한 값과 화면의 실제 활동 기록이 일치한다.

### 8-7. 화면과 제출 자료

- 모바일 너비에서도 네 화면의 주요 기능을 조작할 수 있다.
- 상태 배지는 색을 보지 않아도 텍스트로 의미를 알 수 있다.
- 계획 화면, 대시보드, 활동·출석 화면을 읽을 수 있는 크기로 캡처한다.
- README에 구현한 필수·선택 기능과 실행 방법을 기록한다.

## 9. 기술 경계

- HTML, CSS, JavaScript만 사용한다.
- 데이터는 브라우저 `localStorage`에만 저장한다.
- 차트에는 Chart.js CDN만 사용한다.
- 날짜, D-day, 주간 범위 계산은 JavaScript 표준 API로 처리한다.
- 서버, 데이터베이스, 로그인, 빌드 도구는 도입하지 않는다.
- API 키나 비밀번호가 필요한 기능은 추가하지 않는다.
