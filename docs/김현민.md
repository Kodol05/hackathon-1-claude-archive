| 어떤 결과를 받았나 | 팀원이 올린 조회 기능(`sortActivitiesByDate`, `renderActivityList`)을 먼저 `git pull`로 받아 확인한 뒤, 그 코드를 고치지 않고 활동 등록 기능만 덧붙였다. 이어서 로컬 서버로 앱을 띄워 빈 활동명·공백만 입력·미래 날짜·인원 0·인원 소수를 직접 넣어 차단되는지 확인하고, 정상 등록 시 목록 반영·폼 초기화·새로고침 후 유지까지 확인한 뒤 커밋했다. |
| 만족스러웠는지 | 만족스러웠다. "확인한 다음, 문제없으면 이어서 작업하고 커밋까지"라는 조건을 걸었더니 검증과 구현이 한 번에 처리되었다. 특히 팀원 코드를 건드리지 않고 추가만 한 덕분에 병합 충돌이 나지 않았다. |

## 3. 오류 해결 사례

| 구분 | 내용 |
|---|---|
| 발생한 오류 | 커밋을 여러 번 한 뒤 `git log --format='%an'`로 확인했더니, 내가 올린 커밋 16건의 작성자가 모두 **`unknown`**으로 기록되어 있었다. 제출 요건이 "팀원 전원의 커밋 기록 확인 가능"이라 요건 위반이 될 수 있는 상황이었다. |
| 원인 파악 과정 | `git config user.name`과 `git config user.email`을 확인한 결과, **이메일은 설정되어 있었지만 이름이 비어 있었다.** 다음으로 GitHub API(`gh api repos/.../commits`)로 실제 저장소 쪽 상태를 조회해, 커밋이 계정과 연결되어 있는지 따로 확인했다. |
| 해결 방법 | API 조회 결과 `author.login`이 `Kodol05`로 나와, **GitHub은 이름이 아니라 이메일로 계정을 연결**한다는 것을 확인했다. 즉 제출 요건 자체는 충족된 상태였다. 이미 팀원들이 `pull` 받은 뒤라 히스토리를 다시 쓰면(force push) 팀원 작업과 충돌할 위험이 컸으므로, 과거 커밋은 그대로 두고 `git config user.name "김현민"`을 설정해 이후 커밋부터 이름이 남게 했다. 추가로 README에 팀원별 GitHub 계정을 명시해 채점자가 바로 확인할 수 있게 했다. |
| 배운 점 | 첫째, **작업을 시작하기 전에 `git config`부터 확인해야 한다**는 것을 배웠다. 둘째, 눈에 보이는 증상(`unknown`)만 보고 바로 고치려 들지 않고 실제 영향 범위를 먼저 확인한 것이 중요했다. 확인 없이 히스토리를 다시 썼다면 이미 진행 중이던 팀원 작업까지 망가뜨릴 뻔했다. 되돌리기 어려운 작업일수록 원인 확인이 먼저다. |

## 4. 프롬프트 개선 사례

| 구분 | 내용 |
|---|---|
| 처음 요청한 내용 | "역할부분은 김현민이 백엔드 쪽을 위주로 작업하고 정호님이 프론트 앤드쪽으로 작업하고 재웅님이 보고서 작성 (…) 해당 역할대로 github 커밋 해줄래?" |
| 결과가 기대와 달랐던 지점 | 요청대로 역할이 정리되긴 했지만, 이 프로젝트는 서버와 데이터베이스를 쓰지 않고 `localStorage`만 사용한다. 그래서 "백엔드"에 해당하는 영역이 따로 없고 데이터 로직과 화면 로직이 결국 같은 `app.js`·`index.html` 안에 함께 들어간다. 레이어로 나누면 두 사람이 같은 파일의 같은 구역을 동시에 고치게 되어 충돌이 날 수밖에 없었다. |
| 요청을 어떻게 고쳤는지 | 먼저 "프론트 엔드와 백엔드를 나누는데 서버, DB는 안쓰니까 둘이 작업할때 겹치는 문제가 있지않을까"라고 되물어 구조상의 문제를 짚었고, 이어서 **"기능단위로 분할해서 개발하는걸로 바꾸자"**라고 요청을 바꿨다. |
| 고친 뒤 무엇이 달라졌는지 | 등록·조회·삭제를 한 사람이 하나씩 맡아 HTML·CSS·JS를 끝까지 책임지는 방식으로 바뀌었다. 각자 담당 구역을 주석으로 미리 갈라둔 뒤 작업하니, 같은 파일을 동시에 수정했는데도 **자동 병합으로 처리되어 충돌이 한 번도 나지 않았다.** |

## 5. 소감

규모가 작은 프로젝트라도 여러 명이 함께 작업하니 협업 자체에 요구되는 지식이 생각보다 많다는 것을 느꼈다. 특히 처음에 구조와 규칙을 제대로 잡아두고 일을 나누는 편이 훨씬 효율적이며, 상황에 따라 나누는 방식도 달라져야 한다는 것을 알게 되었다. 실제로 이번에도 레이어(프론트/백엔드)로 나눴다가 기능 단위로 바꾸고 나서야 충돌 없이 작업이 진행되었다.

협업이기 때문에 힘든 부분도 있었지만, 이 과정을 거치면서 앞으로의 해커톤에서는 협업을 더 잘할 수 있을 것 같다. 처음 만난 분들과 함께 작업해 본 것 자체도 좋은 경험이었다.
